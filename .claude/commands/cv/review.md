# /cv:review — レビュー

開発フローの 3 段目。機械的な検証と、観点に沿った自己レビューを行う。

## 1. 検証コマンド

`.claude/skills/verify/SKILL.md` に従って検証を回す。**このファイルにコマンドと基準を再掲しない。**

落ちた段があれば、そこで止めて直してから続きに進む。直さない場合は 3 で理由を報告する。

## 2. セルフレビューの観点

### 範囲

- 計画にない変更が混ざっていないか
- 整形のみの差分が本筋の変更に紛れていないか
- 1 つの PR に収めるべきでないものが入っていないか（`.claude/skills/naming-conventions/SKILL.md` の「1 つの PR に入れる範囲」）

### このリポジトリ固有の落とし穴

`CLAUDE.md` の「作業時の注意点」を 1 つずつ突き合わせる。

- `println!` / `eprintln!` を新たに足していないか
- 設定構造体にフィールドを足したなら `#[serde(default)]` が付いているか
- `update()` の中に重い処理（ディスク I/O、デバイス列挙、画像エンコード、デバイスオープン）を足していないか
- 複数の `Mutex` をネストして取っていないか。取っているなら順序は `settings` → `video` → `audio` → `screenshot` か
- 別スレッドへ処理を移したなら、ロック順序とパニック時の挙動を確認したか

### 品質

- 実装とコメントが一致しているか。**このリポジトリはコメントが実態と食い違っている前科が複数ある**ので、自分が書いたコメントは特に疑う
- デッドコード、コメントアウトした残骸、TODO を残していないか
- エラーを握り潰していないか。`let _ =` や `if let Ok(..)` で失敗を黙って捨てていないか

### テスト

`.claude/skills/testing-conventions/SKILL.md` に照らす。

- バグ修正なら、再現するテストが先にあり、修正前に落ちることを確認したか
- 期待値を実装と同じ式で計算していないか
- 境界値と異常系が入っているか

### ドキュメント

- `README.md` に書かれた挙動を変えたなら、README も直したか
- `docs/MANUAL-TEST.md` の「既知の不具合により失敗する項目」を解消したなら、その節から外して上のチェックリストへ移したか
- `CLAUDE.md` の記述が古くならないか

### 実機確認

コードを読むだけでは判断できない変更か判定する。該当するなら、`docs/MANUAL-TEST.md` のどの項目を確認すべきかを名指しで提示する。

映像・音声・デバイス接続・ホットキー・ウィンドウ操作に触れる変更は、原則として実機確認が要る。

## 3. 報告

- 検証の結果（`.claude/skills/verify/SKILL.md` の「報告」に従う）
- 観点ごとの指摘。**指摘は直すか、直さない理由を述べるかのどちらかにする。** 挙げただけで放置しない
- ユーザーに実機確認を依頼する項目

指摘を直した場合は、**元のコミットを直さず追加のコミットとして積む**（`.claude/skills/naming-conventions/SKILL.md` の「履歴を作り直さない」）。

問題がなければ `/cv:pr` へ。
