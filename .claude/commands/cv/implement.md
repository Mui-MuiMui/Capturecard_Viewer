# /cv:implement — 実装

開発フローの 2 段目。承認された計画をコードにする。**まとまった単位ができたらコミットしていく。**

## 前提の確認

承認済みの計画がこのセッションにあることを確認する。ない場合は `/cv:plan` から始めるよう伝えて止まる。計画なしで実装を始めない。

## 手順

### 1. worktree を切る

`EnterWorktree` で worktree を作り、`.claude/skills/naming-conventions/SKILL.md` の規約に従ってブランチ名を付け直す。`EnterWorktree` は `worktree-` を自動で付けるため、`git branch -m <type>/<英語ケバブケース>` で改名する。

**作業ブランチは `dev` から切る。** `EnterWorktree` は既定で `origin` の既定ブランチから作るため、`dev` を起点にできているか確認し、違えば `git reset --hard origin/dev` で合わせる。

### 2. 計画の範囲だけ実装する

- 計画に書いていない変更をしない
- 途中で別の問題を見つけたら、**手を出さずに記録する。** 実装後に報告し、Issue として起票するか判断してもらう
- 範囲を広げる必要が出たら、実装を止めて相談する

### 3. 実装中に守ること

`GUARDRAIL.md` の項目と `CLAUDE.md` の「コーディング規約」に従う。理由が知りたくなったら `docs/design/` の該当するファイルを読む。特に頻出するもの。

- **`println!` / `eprintln!` を新たに足さない。** `#![windows_subsystem = "windows"]` のため出力先がなく、デバッグの役に立たない。ログ基盤が入るまでは、必要なら一時的に使って必ず消す
- **設定構造体にフィールドを足すなら `#[serde(default)]` を付ける**
- **`update()` の中に重い処理を置かない。** ディスク I/O、デバイス列挙、画像エンコードは別スレッドか、間隔を空ける
- コメントは日本語で書く
- 実装とコメントが食い違っている箇所に気付いたら、その場で直す

### 4. テストを書く

計画で決めたとおりに書く。`.claude/skills/testing-conventions/SKILL.md` に従う。

バグ修正なら、**先に再現するテストを書いて落ちることを確認してから**直す。

### 5. まとまった単位でコミットする

`.claude/skills/naming-conventions/SKILL.md` の「コミットの考え方」に従う。

- **ビルドとテストが通る状態でコミットする。** 壊れた状態や、次のコミットと合わせないと動かない状態を積まない
- 計画の手順 1 つ分が終わったらコミットする、程度の粒度でよい
- 作業を中断したいだけならコミットせず、worktree をそのまま残す

```bash
cargo build
```

```bash
cargo test
```

### 6. 完了時に報告する

- 実装したもの、積んだコミットの一覧
- 計画から変えたことがあれば、その理由
- 範囲外として見送った発見（Issue として起票する候補）

## やらないこと

- push と PR 作成（`/cv:pr` の仕事）
- 計画にない変更
- 自分の変更と無関係なファイルの整形だけを目的にした変更を混ぜる（整形のみの変更は単独 PR にする）
- ビルドやテストが通らない状態でのコミット

実装できたら `/cv:review` へ。
