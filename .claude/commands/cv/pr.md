# /cv:pr — PR 作成とレビュー対応

開発フローの 4 段目。書式はすべて `.claude/skills/naming-conventions/SKILL.md` に従う。**このファイルに書式を再掲しない。**

PR をまだ作っていなければ「初回」、既にある PR にレビューが付いていれば「レビュー対応」として動く。

## 初回

### 1. 前提を確認する

`/cv:review` が通っていることを確認する。通っていない、または実行していない場合は、その旨を伝えて `/cv:review` を先に実行するか確認する。

コミットされていない変更が残っていないか確認する。残っていれば `.claude/skills/naming-conventions/SKILL.md` の「コミットの考え方」に従ってコミットする。

### 2. 差分を確認する

ブランチに積んだコミットの一覧と全体の差分を目視する。意図しないファイルが混ざっていないか、デバッグ用の一時変更が残っていないかを見る。

### 3. push して PR を作成する

**マージ先は `dev`。** `gh pr create --base dev` を明示する。既定が `main` になっていることがあるため、毎回指定する。

PR 本文の書式は `naming-conventions` skill の「PR タイトル」「PR 本文」に従う。**対応する Issue は `Refs #<番号>` で参照する。`Closes` / `Fixes` は使わない**（理由は同 skill の「`Closes` ではなく `Refs` を使う」）。

本文を `gh pr create` に渡すとき、ヒアドキュメントに `git` という語が含まれると worktree 分離の保護に引っかかることがある。その場合は本文を一時ファイルに書いて `--body-file` で渡し、作成後に削除する。

### 4. Issue と相互リンクする

`~/.claude/skills/github-issues/SKILL.md` に従って、Issue へ PR の URL をコメントする。

- ブランチ名と変更の要点を添える
- **「人間が dev で確認すること」を箇条書きで書く。** マージ後にこれが確認の手順になる
- Issue の一部だけを実装した PR なら、その旨と残りのスコープを明記する
- 対応する Issue がない場合は、ここで起票するか確認する

### 5. 報告する

- PR の URL
- コメントした Issue の番号
- ユーザーに実機確認を依頼する項目（`/cv:review` で挙げたもの）

## レビュー対応

既に PR があり、レビューコメントが付いている場合。

### 1. コメントを読む

```bash
gh pr view <番号> --json comments,reviews
```

行単位のレビューコメントは以下で取得する。

```bash
gh api repos/{owner}/{repo}/pulls/<番号>/comments
```

CodeRabbit（`coderabbitai[bot]`）の自動レビューも同じコマンドで取得できる。**人間のレビューを依頼する前に、CodeRabbit の指摘へ一通り対応しておく。**

### 2. 対応方針を示す

指摘ごとに「直す」か「直さない理由」を示す。**判断が分かれる指摘は、直す前に確認する。**

CodeRabbit の指摘も鵜呑みにせず妥当性を判断する。このリポジトリの方針と合わないものは直さず、4 でその理由を返信する。

### 3. 修正して積む

**元のコミットを直さず、追加のコミットとして積む。** amend と rebase による force push は行わない。何を指摘されて何を直したかが履歴に残っている状態を保つ。

修正後も `/cv:review` の検証コマンドを通してからコミットする。

### 4. PR へ返信する

対応内容を PR にコメントする。指摘に対して何をどう変えたか、直さなかった場合はその理由を書く。

PR の題意が変わった場合はタイトルと本文も更新する。

### 5. Issue へ反映する

方針が変わった、スコープが動いた、新しい課題が見つかった場合は、Issue にも書く。

## マージ後

ユーザーがマージしたら、以下を行う。

1. `dev` を同期する
2. worktree とブランチを削除する（ローカルとリモートの両方）
3. Issue に `status:人間確認待ち` ラベルを付け、Project の Status を「人間確認待ち」にする。**部分実装だった場合はラベルを付けず、残りをコメントして「作業中」のままにする**

**Issue は閉じない。** 閉じるのは人が実機で確認したとき。

具体的なコマンドは `naming-conventions` skill の「PR を出したあとにやること」を参照。

## やらないこと

- マージ（ユーザーが行う）
- auto-merge の有効化
- `main` へ直接 PR を出す（リリース時を除く）
- push 済み履歴の force push
- **Issue を閉じる**（PR 本文に `Closes` を書いて自動で閉じさせることも含む）
