# /cv:plan — 計画

開発フローの 1 段目。**このコマンドではコードを書かない。** 計画を提示して承認を待つところまで。

対象: `$ARGUMENTS`

## 手順

### 1. 対象を特定する

引数が Asana タスクの URL なら、URL 末尾の gid で `get_task` を呼んで内容を取得する。
引数が自由記述なら、対応する Asana タスクが既にないか `get_tasks` で確認する。なければ、計画提示時に「新規タスクとして登録するか」を併せて確認する。

引数が空なら、何に着手するかを尋ねて止まる。推測で始めない。

### 2. タスクの記述が今も有効か確認する

**必須。省略しない。**

Asana のタスクには `src/audio.rs:157` の形式で該当箇所が書かれている。バックログは作成時点のスナップショットなので、別の変更で既に解消されていることがある。

- 記載された箇所を実際に読む
- 症状の原因が今もそこにあるか確認する
- 食い違っていたら、その事実を最初に報告する。計画を立てる前に前提を直す

### 3. 影響範囲を洗い出す

このリポジトリで特に見落としやすい観点。詳細は `CLAUDE.md` の「作業時の注意点」を参照。

- **設定構造体に触るか** — `AppSettings` 配下にフィールドを足すなら `#[serde(default)]` が必須。付け忘れると既存ユーザーの設定が全消去される
- **ロック順序に影響するか** — `settings` / `video_capture` / `audio_capture` / `screenshot_manager` の取得順。処理を別スレッドへ逃がす変更なら必ず検討する
- **UI スレッドをブロックするか** — 毎フレーム呼ばれる `update()` の中に重い処理を置かない
- **スレッド境界をまたぐか** — nokhwa / cpal のコールバックは別スレッド
- **ドキュメントとの整合** — `README.md`、`docs/`、`docs/MANUAL-TEST.md` に記述がある挙動を変えるなら、同じ PR で直す
- **既知の不具合との関係** — `docs/MANUAL-TEST.md` の「既知の不具合により失敗する項目」を解消するなら、その節から外す作業も計画に含める

### 4. テストの要否を決める

`.claude/skills/testing-conventions/SKILL.md` の「テストを追加する判断」に従う。

バグ修正なら、**再現するテストを先に書く**ことを計画に明記する。

### 5. 計画を提示する

以下を示して、承認を待って止まる。

- 対象と、現状の確認結果（記述が有効だったか）
- 方針。選択肢が複数あるならトレードオフを添えて推奨を 1 つ出す
- 変更するファイルの一覧
- 実装の手順
- テストの有無と内容
- 実機確認が必要か。必要なら `docs/MANUAL-TEST.md` のどの項目か
- 計画に含めないと判断したこと（範囲外として切ったもの）

## やらないこと

- コードを書く、ファイルを変更する
- worktree やブランチを作る
- 承認前に次の段階へ進む

承認されたら `/cv:implement` へ。
