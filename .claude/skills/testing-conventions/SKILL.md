# テストの方針

Capturecard_Viewer はキャプチャーデバイスと音声デバイスに強く依存するため、一般的な「ユニット / 結合 / E2E」の 3 層では線が引けない。**CI で自動実行できるか**で分ける。

| 区分 | 実行場所 | 対象 |
|---|---|---|
| ユニットテスト | CI で常時実行 | デバイスに触らない純粋関数 |
| 結合テスト（CI 可） | CI で常時実行 | ファイル I/O やスレッド間のやりとりで、実機が要らないもの |
| 結合テスト（実機必須） | 手動。`#[ignore]` を付ける | デバイスを開く・ストリームを流す処理 |
| 手動テスト | リリース前に人が実施 | UI 操作を伴う一連の動作 |

デバイスを掴む処理を CI で回そうとしない。GitHub Actions のランナーにキャプチャーボードもオーディオ入力もない。

## ユニットテスト

### 対象

デバイスにも `%AppData%` にも触らない純粋関数。現時点で対象になるのは以下。

| 関数 | 見るべき観点 |
|---|---|
| `video::yuy2_to_rgb_naive` | 既知の YUYV パターン → 期待 RGB、幅が奇数、データ長が不足、値が飽和する入力 |
| `hotkey::parse_hotkey` | `"F5"`、`"Ctrl+S"`、`"Ctrl+Shift+A"`、修飾キーのみ、空文字、未知のキー |
| `hotkey::parse_key_code` | 対応キー全種、大文字小文字、未対応キーがエラーになること |
| `ui::duplicate_hotkey_actions` | 重複なし、2 つが同じキー、大文字小文字や修飾キーの順序が違う同じキー、空 |
| `settings::get_screenshot_path` | 同名ファイルが既にある場合の連番付与、連番が 2 つ以上続く場合 |
| `calculate_aspect_ratio_size` | 画像が横長 / 縦長 / 同比、利用可能サイズの幅または高さが 0 |

### 書き方

- テストは対象と同じファイルの末尾に `#[cfg(test)] mod tests` を置く
- テスト名は `fn <対象>_<条件>_<期待結果>()` の形にする。日本語は使わない

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parse_hotkey_modifier_only_returns_error() {
        // 修飾キーだけでは登録できないため、パース時点で弾く
        assert!(parse_hotkey("Ctrl+Shift").is_err());
    }
}
```

- **境界値と異常系を必ず入れる。** 正常系だけのテストはリグレッションをほとんど捕まえない
- 期待値をコード中の式で計算しない。ベタ書きする。実装と同じ式で期待値を作ると、実装が間違っていても通る
- ファイルを作るテストは `tempfile` クレートの `tempdir()` を使い、ユーザーのデスクトップや `%AppData%` に書かない

### テストしないもの

- egui の描画結果（見た目）。`ui.label()` が呼ばれたかを検証しても壊れ方を捕まえられない。項目が出る・押すとイベントが返る、は下の「ウィジェットのテスト（egui_kittest）」で書く
- 外部クレートの振る舞い（cpal がデバイスを返すか、nokhwa が列挙できるか）
- 単なるゲッターや `Default` 実装

## 結合テスト（CI で回せるもの）

対象は「複数の部品をまたぐが実機は要らない」もの。

**現状 `tests/` ディレクトリは使えない。** このクレートは `[[bin]]` だけで lib ターゲットを持たないため、`tests/` からは `src/` のコードを参照できない。lib への分割が済むまでは、この区分のテストも対象と同じファイルの `#[cfg(test)] mod tests` に置く。

- **設定の読み込み** — 実装済み（`src/settings/`。読み込みと退避は `store.rs`、欠けた項目は各セクションのファイル）。項目やセクションが欠けた設定ファイルでも残りの値が保持されること、読めなかったファイルが `.bak` へ退避されること。`AppSettings::load` / `save` は `%AppData%` を直接読み書きするため通さず、パスを取る `load_from` / `save_to` と TOML 文字列・`tempdir()` で検証する。**ユーザーの実際の設定ファイルに触れるテストを書かない**
- **`FrameBuffer` のスレッド間動作** — 別スレッドから `push_back` しながら `take_front` して、パニックせず最新フレームが取れること
- **フェイクデバイスを通す** — 実装済み。既知のテストパターンを実機と同じ `FrameSink` へ流して RGB の期待値を確かめる（`src/video/test_pattern.rs`）、ワーカー本体（`worker_loop::run`）にフェイクのバックエンドを載せて再試行から映像が届くまでを通す（`src/app/backend/fake.rs`）。**実機の代わりにデバイスの振る舞いが要るテストはフェイクで書き、`#[ignore]` を付けない。** ワーカーの分岐だけを見るなら、中身を作らないモック（`app::backend::mock`）のほうが軽い。フェイクの仕組みは `docs/design/device-worker.md` の「フェイクデバイス（#142）」

## 結合テスト（実機必須）

デバイスを開く処理は `#[ignore]` を付けて、CI では実行されないようにする。コードとして残しておくことに意味があるので、消さない。

```rust
#[test]
#[ignore = "キャプチャーデバイスが必要"]
fn start_capture_opens_stream() {
    // 実行: cargo test -- --ignored
}
```

- 何が必要かを `#[ignore = "..."]` の理由文字列に必ず書く
- 実行方法を README ではなく、このファイルとテスト自身のコメントに書く

## ウィジェットのテスト（egui_kittest）

設定ダイアログと右クリックメニューの「項目が出る・押すとイベントが返る」は、`egui_kittest`（#419）で CI に載せる。AccessKit の木から項目を名前で探してクリックし、描画関数が返した `SettingsEvent` / `MenuAction` とドラフトを確かめる。区分は「ユニットテスト」と同じく CI で常時実行。

- **版は egui と揃える**（`[dev-dependencies]` の `egui_kittest = "0.36"`）。egui を上げるときは一緒に上げる
- **既定のフィーチャは切ってある。** 画像の比較（`snapshot` / `wgpu`）は使わない。GPU の無い CI でも動き、増えるクレートは `egui_kittest` と `kittest` の 2 つだけ

### 書くもの

- 描画関数の分岐のうち、**利用者から見て壊れると困るもの**。項目の並び（先頭に何が出るか）、選べない項目が灰色で押しても何も起きないこと、押したときに返るイベント、注意書きが出る・消える条件
- egui の版を上げたときに挙動が変わりうるもの。例: サブメニューの項目を押しても閉じない（egui 0.32 の `MenuButton` の既定は押すと閉じる）

### 書かないもの

- 見た目（色・余白・幅・位置）。木には出ないので確かめられない。画像の比較もしない
- 文言そのもの。探すときは `Text::X.get()` や `crate::i18n` の関数で作った文字列を使い、テストに日本語の UI 文字列を写さない（テストで言語を切り替えないこと。`static LANGUAGE` を共有しているので並列のテストが揺れる）
- 映像と音声。映像は `ui.painter().image()` の直接描画で木に現れない
- `app` 側の処理（イベントを受けてからワーカーへ渡す、設定を保存する）。描画関数が返すところまでにする

### 組み立て方

- **描画関数の引数の形はテストのために変えない。** 本番と同じ呼び方で描く
- 設定ダイアログは `src/ui/testing.rs`（`#[cfg(test)]`）の `DialogFixture` と `dialog_harness` を使う。ドラフト・開くタブ・`VideoPinChoice`・入力デバイスの一覧を渡すと、`show_settings_dialog` を毎フレーム描いて返った `SettingsEvent` を `events` に溜める。ドラフトは `fixture.draft()` で読む
- 右クリックメニューは状態を持たない描画関数なので、`MenuView` を組み立てて `menu_items_collapsed` / `menu_items_flat` を `Harness::builder().build_ui_state(..)` で直接描く（`src/app/menu/items.rs` のテスト）
- テストは描画の対象と同じファイルの `mod tests` に置く（1 ファイル 1 つの決まりは同じ）
- 項目は `get_by_label` で探して `click()` し、`harness.run()` で処理させる。灰色かは `node.accesskit_node().is_disabled()`、チェックの状態は `toggled()`、ラベルの文字は `Role::Label` の `value()` で見る（`Label` は既定の `get_by_label` では見つからない）
- **クリックは押下と離しで別のフレームになる。** 「押したあとのフレームで何が返らないか」を見るときは、`events` を空にしてから `harness.step()` を 1 回回して見る

## 手動テスト

UI 操作を伴う確認のうち、上のウィジェットのテストで確かめられないもの（見た目、ウィンドウやデバイスとの組み合わせ、操作感）は自動化しない。`docs/MANUAL-TEST.md` のチェックリストに従ってリリース前に実施する。

## テストを追加する判断

以下に当てはまるなら書く。

- バグを直すとき。**再現するテストを先に書いてから直す。** 直してからでは、そのテストが本当に落ちていたか確認できない
- 純粋関数を新しく作ったとき
- 境界条件が絡むロジック（ゼロ除算、バッファ長、連番付与）を触ったとき

以下なら書かなくてよい。

- UI のレイアウト調整のみ
- ログ出力の追加・変更
- コメントやドキュメントのみの変更

## 実行

```bash
cargo test
```

```bash
cargo test -- --ignored
```

実機必須のテストは 2 つ目のコマンドで、キャプチャーボードを接続した状態で実行する。
