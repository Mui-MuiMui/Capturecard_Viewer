# ログと panic

コンソールが無いこのアプリでデバッグ出力をどこへ出すか、レベルをどう使い分けるか。
`panic = "abort"` の結果として `catch_unwind` が効かないことと、その代わりに何で担保するか。
目指す姿は `docs/ARCHITECTURE.md` の「エラーとログ」にある。

## 標準出力は届かない。ログは log クレートを使う

`src/main.rs` 冒頭に `#![windows_subsystem = "windows"]` があるためコンソールが存在せず、`println!` / `eprintln!` の出力はどこにも届かない。**デバッグ目的で `println!` を足さないこと。**

代わりに `log` クレートのマクロ（`error!` / `warn!` / `info!` / `debug!` / `trace!`）を使う。`main()` の先頭で `logging::init()` を呼んでおり、出力先は設定ファイルの隣。

```
%AppData%\capturecard_viewer\logs\capturecard_viewer-YYYYMMDD-HHMMSS.log
```

- 環境変数 `CAPTURECARD_VIEWER_CONFIG_DIR` で設定の置き場所を差し替えたときは、そのフォルダの `logs\` に出る（`docs/design/settings.md` の「置き場所の差し替え」）。使っている設定ファイルのパスは起動の行の次に出る
- **1 回の起動につき 1 ファイル。** 起動時に新しいものから 10 個だけ残して古い世代を削除する。同じ秒に 2 つ起動した場合は `_1` から始まる連番が付き、互いのログが混ざらない
- レベルは環境変数 `CAPTURECARD_VIEWER_LOG`（`error` / `warn` / `info` / `debug` / `trace`、既定 `info`）。解釈できない値は `info` に倒れる。設定ファイルには持たせていない
- `panic = "abort"` で終了時のフラッシュが走らないため、1 行ごとにフラッシュしている
- `symphonia` で始まるターゲット（効果音のデコード）の ERROR / WARN は INFO に落として出す。デコードの失敗はアプリ側でも拾って WARN を出すため、二重に見えないようにしている。捨てはしないので、レベルが `info` / `debug` / `trace` なら読める（`warn` / `error` では出ない）（`src/logging.rs` の `effective_level`）
- `logging::init()` が失敗してもアプリは起動する。ログが無いだけで機能には影響しない

レベルの使い分け。

| レベル | 使う場面 |
|---|---|
| `error` | 復旧できない失敗。ストリームのエラー、設定の保存失敗、ホットキーの登録失敗 |
| `warn` | 続行できるが想定外。フォールバックした、ロックを取れなかった |
| `info` | 状態の遷移。デバイスの接続、キャプチャの開始と停止、確定した設定値 |
| `debug` | 経過の詳細。デバイスの探索、スレッドの起動と終了 |
| `trace` | 毎フレーム・毎イベント流れるもの。ホットキーイベントの受信、2 秒ごとの再適用、フレームの到着 |

**アプリ本体に `println!` / `eprintln!` は 1 つも残っていない。** 足し直すと CI で落ちる。`Cargo.toml` の `[lints.clippy]` で `print_stdout` / `print_stderr` を `warn` にしてあり、CI は `-D warnings` で clippy を回すため。

**例外はテストコードの中。** テストバイナリの標準出力は `cargo test -- --nocapture` で読めるため、`println!` を使ってよい（`src/video/convert.rs` の計測用テストがその例）。`src/main.rs` 冒頭の `#![cfg_attr(test, allow(clippy::print_stdout))]` がこれを許している。**クレートルートに置いてあるのは、テストを持つモジュール側に `#[allow]` を散らかさないため。**

**デバイス起因の不具合を調べるときは `.claude/skills/device-debug/SKILL.md` の手順に従う。** ログの読み方、正常時の所要時間の目安、症状ごとの確認順をまとめてある。

## 繰り返し出るログは出す側で間引く。1 ファイルの大きさに上限は設けない（#506）

**繋がらないデバイスの再試行は、最大 5 秒間隔で繋がるまで続く**（`docs/design/reconnect.md`）。以前は試行のたびに「接続を試す（N 回目）」（INFO）と「接続に失敗した（N 回目）」（WARN）を出していたので、ボードを外したまま起動しておくと 1 台につき 1 日 1.7 万回の試行と失敗がログに並び、列挙のログ（50 秒に 1 度、4 行）も加わって、1 回の起動の 1 ファイルが際限なく大きくなった。

- **INFO / WARN で出すのは節目の回だけにした。** 1〜3 回目・5 回目・10 回目から 100 回目までは 10 回ごと・以後 100 回ごと（`src/app/retry.rs` の `is_retry_log_milestone`）。それ以外の回は DEBUG に落とすだけで、捨てない。`CAPTURECARD_VIEWER_LOG=debug` なら全部読める
- **失敗の理由が前回と変わった回は、節目でなくても WARN で出す**（`connect_failure_log_level`）。比べる相手は直近の失敗の理由（`last_video_failure` / `last_audio_failure`）で、繋がったら消えるので、次に失敗し始めた 1 回目は必ず出る。回数も繋がったら 0 から数え直す
- **繋がった行（`映像デバイスに接続した（N 回目、M ms）`）は必ず INFO で出し、何回目で繋がったかとその試行にかかった時間を入れた。** 「試す」の行が DEBUG に落ちていても、調査で頼る「何回目で繋がったか」「1 回の試行の所要時間」（`.claude/skills/device-debug/SKILL.md`）が読めるようにするため
- **列挙のログも同じ節目でだけ INFO にした。** 列挙と「Windows 側にも見えていない」の判定はこれまでどおり 5 回目・以後 10 回ごとに行う（判定の間隔は変えない）。経路ごとに前回出した結果（台数と名前）を覚えておき（`last_enumeration_listing`）、変わった経路は節目を待たずに INFO で出す。挿し直して OS 側に戻ったことは、すぐログから読める
- 間引いたあとの量は、映像と音声の両方が繋がらないまま 1 日起動しておいて、試行・失敗・列挙を合わせて INFO / WARN が 2,000 行前後（節目は 1 台あたり 1 日約 185 回。列挙は映像と音声の節目のたびに 4 行）。以前は 8 万行を超えていた（試行と失敗が 2 台で約 6.9 万行、列挙が約 1.4 万行）。計算上の値で、実測ではない

**1 ファイルの大きさの上限は設けない。** 理由は次の 3 つ。

- **超えたときの振る舞いに、良いものが無い。** 書くのを止めると、いちばん欲しい「落ちる直前のログ」（`panic = "abort"` で終了時の処理が走らない）が残らない。次のファイルへ回すと「1 回の起動 = 1 ファイル」が崩れ、世代管理（新しいものから 10 個）の数え方も変わる。長く起動した 1 回だけで直近の他の起動のログを押し出すことになり、不具合報告で「前回の起動のログ」を添えてもらえなくなる
- **ログの量を決めるのは、繰り返し出す処理のほう。** ファイルの上限で抑えても、あふれる原因（毎回出しているログ）はそのまま残り、上限までは同じ行で埋まる。原因の側で間引けば、上限に頼らずに済む
- 書き込みは 1 行ごとにロックを取ってフラッシュしている。大きさを見てファイルを替える処理をそこへ足すと、ロギングの経路が重く、失敗しうる箇所も増える

**繰り返し出るログを足すときは、ここと同じく出す側で間引く。** 回数で間引くなら `is_retry_log_milestone` を使う。時間で間引くなら、最後に出した時刻を状態に持つ（音声の観測値のログ `last_audio_counters_log` と同じ）。

## catch_unwind は使わない

`Cargo.toml` の `[profile.release]` に `panic = "abort"` があるため、`std::panic::catch_unwind` は release ビルドで一切機能しない。パニックが起きればプロセスごと落ちる。

以前は `update()` の中で `ViewportCommand` の送出と `apply_settings` を `catch_unwind` で囲み、失敗を警告に落としているように見えていた。**実際には守っておらず、読む側に「ここはパニックしても続く」と誤解させるだけなので削除した。** 代わりに、囲んでいた処理がパニックしないことを確認してある（`unwrap` / `expect` / 添字が無く、`Mutex::lock()` の失敗も `if let Ok` で受けている）。

**パニックしうる処理を書かない側で担保すること。** `Option` と `Result` は `unwrap` せずに分岐し、ロックの失敗はログに残して諦める。`catch_unwind` を足しても release では効かない。
