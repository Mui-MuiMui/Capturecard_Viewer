# ホットキー

割り当てをアクションごとに持つ設定ファイルの形と、旧形式からの移行。
アクションを増やすときに埋める場所と、登録を差分で行う理由。
押下をキーを奪わずに観測する理由と、フォーカスがあるときだけ反応させる旗、テキスト入力中の扱い、前面にいるときに egui へ渡さない理由。
リスナースレッドの扱いは `docs/design/threads.md` にある。

## ホットキーはアクションごとに持つ

割り当ては `AppSettings::hotkeys`（`BTreeMap<HotkeyAction, String>`）にあり、設定ファイルでは独立した `[hotkeys]` セクションになる。キーは `HotkeyAction::as_str()` の文字列。

```toml
[hotkeys]
screenshot = "F5"
toggle_fullscreen = "Ctrl+F11"
```

- **`[hotkeys]` セクションが無い場合と、空のセクションがある場合は意味が違う。** 前者は旧版が書いた設定ファイル（既定の F5 を入れる）、後者はすべての割り当てを外した状態（何も入れない）。`RawAppSettings::hotkeys` を `Option` で受けているのはこの区別のため
- **既定で割り当てるのはスクリーンショットの F5 だけ。** ホットキーは既定で他のアプリを操作している間も反応するので、こちらから F11 のような一般的なキーを割り当てると、他のアプリでそのキーを押すたびにこちらも動く
- **旧版の `screenshot.hotkey` は読むだけで書き戻さない。** `ScreenshotSettings::legacy_hotkey` が `#[serde(rename = "hotkey", skip_serializing)]` で受け、`[hotkeys]` が無いときだけスクリーンショットへ移す。移行後の最初の保存で旧項目は設定ファイルから消える（新しい版で一度起動すると、古い版へ戻したときはホットキーが既定の F5 に戻る）
- 知らないアクション名は読み飛ばしてログに残す。エラーにすると設定ファイル全体が読めなくなる
- **読み込みは `#[serde(from = "RawAppSettings")]` を通る。** どの経路で読んでも移行が走るようにするためで、`AppSettings` に項目を足すときは `RawAppSettings` と `From` にも足すこと

アクションを増やすときは `HotkeyAction` に variant を足し、`ALL` / `as_str` / `label` / `runs_while_minimized` の 4 か所と、`folded_repeats`、`src/app/hotkeys.rs` の `run_hotkey_action` と `background_hotkey_runner` を埋める（後ろの 4 つは「最小化中の扱い」を参照）。**`as_str` の文字列は設定ファイルに書かれるので、一度出した名前は変えない。** 実行は右クリックメニューや映像上の操作と同じメソッドを呼ぶこと（`set_always_on_top` / `adjust_volume` / `reconnect_devices` / `toggle_fullscreen`）。独自に書くと、同じ操作なのに設定の保存やオーバーレイ表示の有無が経路で変わる。

登録（リスナーが照合に使う表へ載せること。OS へは何も登録しない）は `HotkeyManager::apply` が差分だけ行う。2 秒ごとに呼ばれるため、無条件に登録し直すとその瞬間の入力を取りこぼす。登録できなかったものは `errors()` に残り、設定画面に理由が出る。**直るまで毎回試し直すが、ログに出すのは理由が変わったときだけ**（同じ失敗が 2 秒ごとに積もらないように）。

**`HotkeyManager::apply` を直接呼ばないこと。** 呼ぶのは `CaptureCardViewer::apply_hotkey_assignments` だけで、そこで `report_error(ErrorSource::Hotkey, ..)` によるトースト通知と、全て登録できたときの `ErrorCenter::clear` を行っている。直接呼ぶとこれらが抜ける。設定画面の一覧に出す見出しも `ErrorSource::Hotkey.headline()` を使い、トーストと同じ文言に揃えてある。

## 最小化中の扱い

最小化すると eframe が再描画要求を捨てるため `update()` が呼ばれなくなる（`docs/design/video-pipeline.md` の「再描画をいつ要求するか」）。押下を検出するのはリスナースレッドなので最小化中も止まらないが、**実行は `update()` の `handle_hotkeys` が行っていたため、復帰するまで持ち越されていた**（#133）。接続の再試行と切断の監視はデバイスワーカーへ移して解決済みで（`docs/design/device-worker.md`）、残っていたのがこのアクション実行。

アクションを 2 種に分けて扱う。分かれ目は `HotkeyAction::runs_while_minimized()`。

| 種別 | アクション | 最小化中の扱い |
|---|---|---|
| 画面が要らない | デバイス再接続 / 音量を上げる・下げる / ミュート切替 | その場で実行する |
| 画面が要る | スクリーンショット / フルスクリーン切替 / 最前面表示の切替 | 復帰するまで溜める |

### 画面が要らないものはリスナーからワーカーへ流す

リスナースレッドは `BackgroundHotkeyRunner`（`DeviceCommand` を送る閉包）を持っており、最小化中はそこへ渡す。組み立ては `app::hotkeys::background_hotkey_runner` で、送るのは `ReconnectNow` / `AdjustVolume` / `ToggleMute` の 3 つ。**デバイスワーカーはウィンドウの状態に関係なく動く唯一のスレッドなので、UI スレッドの代役をそこに置いた。**

- **新しい `Arc<Mutex<..>>` は足していない。** 音量とミュートの実体は既に `AudioControls`（Atomic）で、ワーカーはその複製を持っている。最小化しているかは既存の `ListenerState`（リスナーと共有している唯一のロック）へ `minimized` として書く
- **最小化しているかは `update()` の末尾で毎フレーム書く。** 最小化すると `update()` が呼ばれなくなるので、最後に書いた `true` がそのまま残る。これが「最小化中である」ことの表現になっている
- **ワーカーが実行したことは `DeviceEvent::VolumeAdjusted` / `MuteToggled` で UI へ返す。** 復帰した最初のフレームで `adjust_volume` / `toggle_mute` を通るので、設定への反映・OSD・右クリックメニューへの反映は、メニューから操作したときと同じになる（GUARDRAIL の「ホットキーのアクションは右クリックメニューと同じメソッドを呼ぶ」）
- **音量は絶対値ではなく差分（`delta`）で返す。** `AudioControls` が持つのは 0.0〜2.0 の倍率で、パーセントへ戻すと端数が動く（60% が 59.999996% になりうる）。差分なら UI 側の値を正のまま同じ経路へ通せる
- 上下限とミュート解除の判断は UI と同じ `app::audio_control::volume_change_result` を通す。ワーカー側で書き直すと、経路によって上限や解除の有無が変わる
- **ワーカーはコマンドを 1 つずつ処理するので、デバイスを開いている最中（数百 ms）は待たされる。** 最小化中の操作なので許容している。ここが気になるなら、リスナーから `AudioControls` を直接書く形もありうるが、そのときも「UI へ何を返すか」は同じ問題が残る

### 画面が要るものは復帰したときに畳む

保留した押下は `ListenerState::pressed`（`BTreeMap<HotkeyAction, u32>`）に**回数で**溜まる。復帰したときに `take_pressed` が `folded_repeats` で畳む。

- トグル（フルスクリーン / 最前面表示 / ミュート）は**奇数回なら 1 回、偶数回なら実行しない**。2 回押して戻したつもりが復帰時に切り替わる、という食い違いを避ける
- スクリーンショットは何回押されていても 1 枚。撮るのは復帰後の映像なので、何枚撮っても同じ絵になる
- 音量の上げ下げは押した回数ぶん効かせる（最小化中はワーカーが実行するので、ここへ来るのは通常のフレームで溜まった分だけ）

**デバウンス（200ms）はリスナー側で行う**（`ListenerState::record_press`）。以前は `take_pressed`、つまり実行の時点で計っていたが、最小化中は実行が UI スレッドを通らないため、押しっぱなしのキーリピートを落とせない。記録の時点で計れば、どちらの経路でも同じ間引きが効く。

## キーを奪わない（低レベルキーボードフック）

以前は global-hotkey クレート、つまり Win32 の `RegisterHotKey` で押下を検出していた。**`RegisterHotKey` に登録した組み合わせはシステム全体で横取りされ、フォアグラウンドのアプリには届かない。** 非フォーカス時・最小化中も反応させる（#133）と、割り当てたキーが他のアプリで一切使えなくなる（#202）。`RegisterHotKey` の仕様なので、呼び方の工夫では避けられない。

そこで押下の検出を低レベルキーボードフック（`WH_KEYBOARD_LL`）へ置き換えた。実装は `src/keyboard_hook.rs`。**フックは見るだけで、受け取ったキーは必ず `CallNextHookEx` で次へ渡す。** 戻り値も次のフックのものをそのまま返す（非ゼロを返すとキーを握りつぶす）。global-hotkey への依存は外した。

```mermaid
sequenceDiagram
    participant OS as Windows の入力
    participant Hook as フックのコールバック<br/>（リスナースレッド上）
    participant Loop as リスナーのループ<br/>（handle_key_down）
    participant App as 他のアプリ

    OS->>Hook: WM_KEYDOWN（全てのキー入力）
    Hook->>Hook: 押下か / 修飾キーか / キーリピートか
    Hook-->>Loop: PostThreadMessageW（仮想キー + 修飾キー）
    Hook->>App: CallNextHookEx（キーはそのまま届く）
    Loop->>Loop: ListenerState のロックの中で照合・デバウンス・記録
```

- **フックはリスナースレッドに置く。** フックのコールバックは、登録したスレッドがメッセージを取り出すときにそのスレッドの上で呼ばれる。そのためリスナーにメッセージループ（`MsgWaitForMultipleObjects` と `PeekMessageW`）を持たせた。リスナーがアプリ全体で 1 本という決まりは変わらない（`docs/design/threads.md`）
- **コールバックの中ではロックもアロケーションもしない。** システム全体のキー入力が 1 回ごとにこのコールバックを通るので、ここが遅れると他のアプリの入力まで遅れる。Windows は既定の時間（`LowLevelHooksTimeout`）を超えると待たずに次へ渡し、繰り返すと黙ってフックを外す。コールバックが行うのは「押下か（`WM_KEYDOWN` / `WM_SYSKEYDOWN`）」「修飾キーか」「キーリピートか」の判定と、修飾キーの状態を読んで自分のスレッドへ `PostThreadMessageW` で投函することだけ
- **照合から先は従来の経路のまま。** 投函されたメッセージをリスナーのループが取り出し、`ListenerState` のロックの中で照合・デバウンス・押下の記録を行う。最小化中の `BackgroundHotkeyRunner` への受け渡しも同じ（「最小化中の扱い」）。**このループの処理も短く保つこと。** 処理している間は次のキー入力のコールバックが待たされる。ロックは照合と記録の間だけ握り、UI スレッドを起こすこととワーカーへの送信はロックを手放してから行う
- **修飾キーは完全一致で比べる。** `F5` の割り当ては `Ctrl+F5` では反応しない。`RegisterHotKey` と同じで、他のアプリの `Ctrl+F5`（再読み込みなど）でこちらが動かないようにするため
- **キーリピートは数えない**（`RegisterHotKey` に付けていた `MOD_NOREPEAT` と同じ）。低レベルフックの中では処理中のキーの状態がまだ更新されていないので、`GetAsyncKeyState` がそのキーを「押されている」と返すなら、前から押しっぱなしのキーリピートと分かる。デバウンス（200ms）だけに任せると、押している間 200ms ごとに実行される
- **他のアプリとの競合で登録に失敗することは無くなった。** 同じキーを他のアプリが使っていても、両方が反応する。登録の失敗は「解釈できない」「重複している」「フックを使えない」の 3 つだけになり、`HotkeyManager::try_register` は解釈とフックの有無を確かめるだけになった。`RegisterHotKey` ではデバッガ用に予約されていて登録できなかった F12 も割り当てられる
- **このアプリが前面にあるときは egui にもキーが届く。** 以前は横取りされて egui には届かなかった。たとえば Escape を割り当てると、右クリックメニューを閉じる操作と重なる。egui 側で取り除いて抑えてある（下の「前面にいるときは egui へ渡さない」）。テキスト欄に入力中の分は逆に egui へ渡し、ホットキーを止める（「テキスト入力中は反応しない」）
- **管理者として実行しているウィンドウが前面にある間は、フックに入力が届かないとされている**（Windows の UIPI）。`RegisterHotKey` ではこの制限が無かった。実機での確認項目は `docs/MANUAL-TEST.md` の「ホットキー」にある
- **ホットキー入力ダイアログの一時解除（`pause` / `resume`）は残した。** キーは奪わなくなったが、割り当て済みのキーを付け直そうとして押したときに、そのアクションまで実行されるのを防ぐため。照合に使う表を空にするだけで、フックとリスナーは止めない

フックを登録できなかったとき（`SetWindowsHookExW` の失敗）は、リスナーはすぐに終わり、理由を `HotkeyManager` が持つ。以降の割り当てはすべて `HotkeyError::HookUnavailable` として記録され、トーストと設定画面に出る。動いていたリスナーがキー入力を待てなくなって終わったとき（`MsgWaitForMultipleObjects` の失敗）も同じ扱いにする。リスナーは理由を `ListenerState` に書いてから終わり、次の `apply` が拾って `hook_error` へ移し、登録済みのものを外して失敗として記録し直す。**ログだけで終わらせると、効かないのに登録済みのまま何も表示されない。**

## フォーカスがあるときだけ反応する

「ホットキー」タブの「このアプリにフォーカスがあるときだけ反応する」。`HotkeySettings::only_when_focused` で、設定ファイルでは `[hotkey_settings]` になる。

- **既定はオフ。** これまでどおり、他のアプリを操作している間も最小化している間も反応する（#133 の最小化中の操作を保つ）。オンにすると、他のアプリで同じキーを使っていてもこちらは動かない。どちらの場合もキーは奪わない
- **`[hotkeys]` に混ぜない。** あちらは値が全て文字列である前提で読んでいる（`RawAppSettings::hotkeys`）。真偽値が混ざると、旧版では `[hotkeys]` ごと読めなくなる
- **判定はリスナーの `ListenerState::record_press` で行う。** `focused`（フォーカスがあるか）と `only_when_focused`（旗）を `ListenerState` に持つ。`focused` は UI スレッドが `update()` の末尾で毎フレーム書く（`minimized` と同じやり方）。フォーカスを失うと egui-winit が再描画を要求するので、その `update()` で偽が書かれる
- **フックの中で `GetForegroundWindow` を呼んで調べない。** コールバックでは判定以外のことをしない決まりで、自分のウィンドウハンドルをリスナーへ渡す経路も増える。UI スレッドが知っている値を書いておけば足りる
- **最小化中は前面にいないものとして扱う。** 最後に書いた `focused` が真のまま残っていても、`minimized` が真なら捨てる
- **捨てた押下は保留にも残さず、デバウンスの基準も更新しない。** 保留に残すと、戻ってきたときに実行される。基準を更新すると、フォーカスを戻した直後の押下まで捨てられる
- 旗は `apply_settings`（2 秒ごと、と「適用」「OK」の直後）で `HotkeyManager::set_only_when_focused` から渡す。プリセットには入れない（`docs/design/presets.md`）

## テキスト入力中は反応しない

キーを奪わなくなったので、設定ダイアログのテキスト欄（プリセット名、保存先など）に打った文字もリスナーへ届き、修飾キーなしの単キーを割り当てていると入力のたびに実行されていた（#206）。**egui がキーボード入力を受けている間（`Context::wants_keyboard_input()` が真）は押下を捨てる。** UI スレッドが `update()` の末尾で `ListenerState::typing` に毎フレーム書き、リスナーの `record_press` が `rejected_by_window_state` で判定する（`focused` / `minimized` と同じやり方で、フックの中から egui へは問い合わせない）。**入力中の旗は前面にいて最小化していないときだけ見る。** egui はウィンドウがフォーカスを失ってもテキスト欄のフォーカスを手放さないので、入力欄を選んだまま他のアプリへ移ると旗が真のまま残り、そこで捨てると他のアプリの操作中に効かなくなる。捨てた押下は「フォーカスがあるときだけ反応する」と同じく保留にも残さず、デバウンスの基準も更新しない。旗はフレームの末尾で書くので、テキスト欄にフォーカスが移ったフレームの間の押下は偽のままの旗で保留に積まれる。**旗が偽から真へ変わったときに保留を捨てる**（`set_window_state`）。そのキーは次のフレームで egui がテキスト欄へ入れるので、実行すると打った文字がホットキーとしても効く。`wants_keyboard_input()` はテキスト欄に限らず、Tab キーでボタンなどへフォーカスを移した間も真になるので、その間もホットキーは効かない。ホットキー入力ダイアログを開いている間は、これとは別に `pause` で照合の表ごと空にしてある。入力中でないときに egui へもキーが届く件は、次の「前面にいるときは egui へ渡さない」で抑えた

## 前面にいるときは egui へ渡さない

キーを奪わないので、このアプリが前面にある間は割り当てたキーが egui にも届く。Escape を割り当てると右クリックメニューも同時に閉じ、Space や Enter のような単キーはボタンの操作と重なる（#217）。**フックが反応するキーの押下は、egui へ渡す前に取り除く。** `update()` の先頭（描画より前）で `CaptureCardViewer::remove_hotkey_key_events` が `Context::input_mut` の `events` から取り除き、判定は `hotkey::parse::remove_hotkey_key_events`（純粋関数）が持つ。

- **取り除くのはこのアプリの中だけ。** 他のアプリへはこれまでどおりキーがそのまま届く。フックは相変わらず見るだけで、`CallNextHookEx` へ渡している
- **修飾キー付きの割り当て（`Ctrl+Alt+F9` など）でも同じに扱う。** 実害はほぼ無いが、単キーに限る分岐を足すと「何が取り除かれるか」の説明が割り当ての形で変わる。egui 側にそのキーを使う操作が無いので、取り除いても失うものが無い
- **照合は登録中の表（`ListenerState::registered`）で行う。** 「直前にリスナーが発火したキー」を覚えておいて照合する案は採らなかった。フックとリスナーは別スレッドなので、egui へキーが届いたフレームにリスナーがまだ処理を終えていないことがあり、照合が漏れる。表なら押下の前から決まっている。表を見るのでデバウンスで捨てた押下も取り除く（ホットキーのキーであることは変わらない）。ホットキー入力ダイアログを開いている間は表が空（`pause`）なので、押したキーはダイアログへ届く。フックを使えないときも表は空なので、何も取り除かない
- **入力中（`Context::wants_keyboard_input()` が真）は何も取り除かない。** その間はリスナーが押下を捨てている（「テキスト入力中は反応しない」）ので、キーはテキスト欄のもの。旗は `update()` の先頭で読むので、前のフレームの描画を終えた時点の状態になる。リスナーへ渡す旗（末尾で書く）と同じ値
- **取り除くのは押下（キーリピートを含む）だけで、解放は残す。** 押下の無い解放は egui では何も起こさない。キーの押下が無いフレームでは共有状態のロックを取らない
- **egui のキーから `KeyChord` への変換は `Key::name()` を `parse_key_code` に通す**（`parse::chord_from_egui`）。対応表を別に持つと、設定ファイルで受け付けるキーと取り除くキーが食い違う。egui の修飾キーには Windows キーが無いので、`Win+F5` も egui には `F5` として届き、`F5` の割り当てがあれば取り除かれる。Windows キーとの組み合わせはたいていシェルが先に使うので区別しない
- **数字キーは取り除かない。** egui-winit はメイン列の `0` とテンキーの `0` をどちらも `Key::Num0` にするので区別できないが、フックの側ではテンキーは `VK_NUMPAD0` で `0` の割り当てには反応しない。取り除くと、テンキーの `0` がホットキーも発火せず egui にも届かない押下になる。数字は egui ではテキスト入力にしか使わず、その間は取り除かないので、残しても衝突しない
- **`eframe::App::raw_input_hook` は使っていない。** いま使っている eframe 0.26 には無い。`update()` の先頭で `input_mut` から取り除くのと効果は同じだが、egui が `begin_frame` の中で処理するもの（Escape や Tab によるフォーカスの移動）には間に合わない。それらはウィジェットにフォーカスがある間、つまり入力中の扱いになる間だけ起きるので、取り除く対象とは重ならない
